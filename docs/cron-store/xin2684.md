# XIN-2684: classified failure projection and retained retry chains

This is a bounded extension of accepted XIN-2678 at
`a7025f6193006dbe5beda80e6f3ef97cd252ee4b` (tree
`53cd12b2dd75ab7eb3a543273e82f216fc268819`). It does not implement a scheduler,
executor, delivery publisher, alert sender, startup repair or pruning.
Schema, indexes, schedule code, dependencies, lockfile, pins, CI and host code
remain unchanged.

## Explicit API

`CronStore.finalize` accepts a new classified outcome:

```ts
store.finalize(scope, jobId, {
  expected: terminalExpectation(admittedRunningReceipt),
  ownership: alreadyHeldOwnershipProof,
  outcome: { kind: 'failure', reason: 'network', redactedError: 'sanitized error' },
  retryRunId: callerAllocatedRunId,
});
```

`redactedError` is optional; the caller must sanitize it. No external error,
model, SDK or transport is invoked here. Unclassified legacy `error`,
`target-failure`, `restart`, `session-busy` and `retry-superseded` requests keep
their original typed no-write deferral. Existing success and neutral APIs
retain their accepted behavior.

For success/neutral continuation, supply `retryChain: true`. Classified
failures automatically require chain validation. Legacy attempt>0 requests
without this selection still return `deferred/retry-chain` with zero writes;
this compatibility result is not proof of chain integrity.

`admitRetry(scope, jobId, runId, ownership)` explicitly returns
`deferred/retry-admission` with no writes and no execution grant. Finalization
and successor persistence are not admission. Current generation, enablement,
retained active-chain provenance, authority, reset/deadline, ready time,
attempt uniqueness and single-flight must all be proved by a future admission
implementation; it may bypass only the reserved occurrence's base-W gate.
Tests that move a queued successor to running seed that executor precondition.
They do not demonstrate an implemented retry executor or recovery workflow.

## Supported and deferred matrix

All supported operations use existing-receipt exact status/owner/provenance
CAS in the ownership-locked BEGIN IMMEDIATE transaction. Only its one changed
row authorizes effects. Duplicate/different-outcome callbacks return the
stored terminal receipt with no repeated counter, W, retry or deletion.

The exact R8 Q ladder is `[30s, 60s, 5m]`, indexed by the new retry attempt.
Session-busy always uses 30s. The exact B ladder is
`[30s, 60s, 5m, 15m, 60m]`, capped at index4. The latter four B effects cannot
commit here because the earlier alert prerequisite defers execution-error
counts>=2. Having those constants in source is not evidence of those
unavailable effects. Q60s/Q5m are actually tested after prior skipped
session-busy admissions, before the first executed failure. Repeated executed
failures cannot silently bypass the count2 alert gate.

## Concrete atomic-contract prerequisite

There is no accepted same-transaction data-only alert/disable-notice intent
seam in this baseline. `cron_jobs` has aggregate `alert_incident_key`,
`alert_occurrence`, `last_alert_at` markers; the admitted snapshot has no
failure-alert policy or immutable owner/creator notice target. Those fields
alone are not an accepted immutable pending-publication contract. No new
table, host publication, actual alert send or configuration change is allowed
in this slice. Therefore mandatory alert/notice outcomes defer entirely
before CAS. An accepted isolated transactional representation sufficient for
the complete alert/notice obligation is the prerequisite for extending those
rows. No counter-only auto-disable or terminal receipt is committed while
silently omitting that obligation. Full failure-finalizer acceptance remains
blocked on that prerequisite; this increment is independently reviewable only
within the matrix above.

## R8 atomic steps and retention

1. The existing exact CAS remains the only effect gate; ownership is asserted
   at entry and before commit. Transactions are short/synchronous and make no
   external calls.
2. Supported terminal facts and current-generation attempt0 NULL-safe Wmax
   commit together, including consuming manual base receipts. W is never
   cleared/lowered. Older completion cannot regress later overlap cadence.
3. Supported classified counters/cadence commit once through the shared
   `projectTerminal` writer. Mandatory alert/notice branches defer before CAS.
   Retry success shares success resets and owner-fenced one-shot retirement.
4. Borrow/none/stale/tombstone remain informational only.
5. Before a continuation, read all retained occurrence attempts. Require
   canonical validated attempt0, contiguous attempts through the active run,
   identical definition/manual/authored/reset provenance, retryable terminal
   predecessors and exact ready/queued timing. Missing/corrupt/future chain
   members raise actionable integrity/quarantine errors with no writes.
   Current retries assert committed base W. Terminalize current first; only
   then insert attempt+1 with the same occurrence/snapshot/authored slot in
   the same transaction. Collision or fault rolls everything back. Active
   chains must remain retained; no pruning implementation is added.
6. None/suppression/not-delivered history records are honest no-publication
   states. Delivered-history/reset-fenced ContextNotes remain deferred.

These are store-level proofs for §§3.4.1–5/3.4.7–8/10.6/10.9. They do not
complete DEV09–11, the scheduler/manual/startup/pruning workflows, or full
REPLAY/BOUNDARY/OP end-to-end acceptance. Store SQL observations are not the
independent model/egress oracle.

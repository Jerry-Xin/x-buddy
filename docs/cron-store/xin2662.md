## API and transaction contract

`CronStore.admitBase(scope, jobId, request)` accepts only scheduled/catchup
attempt0 reservation. It runs synchronously in `BEGIN IMMEDIATE` and commits
the queued receipt and natural cadence update together. It rereads the current
scoped job, enabled/tombstone/generation state and normalized definition inside
that transaction. All schedule calculations use the accepted effective-slot
functions, including the resolved cron stagger. No pre-transaction candidate
or definition observation grants admission.

The request supplies an explicit effective `slot`, expected `generation`,
unique `runId`, validated authority snapshot and held-ownership proof.
Authority includes the exact job ID/definition, positive creator/target
decisions, incarnation, reset generation and frozen policy inputs. The policy
seam accepts the R8 TurnContext tools selector and optional egress allowlist;
it contains no credentials. Authority and ownership incarnation/reset values
must agree. `assertHeld()` is a synchronous proof seam checked inside the
transaction and before committing a new reservation or returning a stored
receipt. The caller must actually hold the bot ownership lock throughout;
this library does not acquire that lock, resolve bot authority, inspect a
session reset table, terminate previous children or grant a model permit.

For a fresh base, the effective slot must be due, at/after activation and not
before `next_run_at`. `scheduled` uses the stored natural slot exactly;
`catchup` uses only the latest effective slot at/before observed time.
Scheduled recurring admission projects `next(S)`; catch-up projects `next(now)`.
An at receipt preserves its original authored `next_run_at`. Reservation
never advances W, changes counters/last outcomes, publishes history or
terminalizes work. The complete row has canonical identity
`JSON.stringify([jobId,generation,slot])`, consume ownership, immutable
definition/policy/admitted fields, attempt0 and `ready_at=slot`. Owner/reset
are captured in the existing receipt columns. SQLite defaults supply the
initial null phase/outcomes and not-started delivery with zero segments.

Results are:

- `reserved`: a newly committed queued receipt; subsequent execution remains
  subject to runtime generation/authority/ownership checks outside this slice.
- `existing`: the exact stored row/outcome, including its original owner,
  reset generation, trigger, snapshot and timestamps. It is a lookup result,
  not permission to start or recover execution. A valid lower-slot reservation
  remains identifiable behind a later W/cadence, or after a backward clock
  change. A matching consuming manual receipt also dedupes a timed request.
- `already-consumed`: no receipt exists and current-generation S≤W. No state
  changes, even when display history is absent. This does not establish how
  W was originally committed or authorize pruning.
- `deferred`: no mutation. The reason is `one-shot-busy`,
  `recurring-overlap`, or the separately classified
  `queued-retry-supersession`, with the active run ID and a 30000 ms recheck
  ceiling. The caller must implement bounded wake scheduling and immediate
  wake when single-flight clears; no timer/wake loop is implemented here.

Retained receipt lookup precedes fresh watermark/cadence/time eligibility.
Canonical and slot-index claims must identify one consistent attempt0 receipt.
Malformed/mismatched stored provenance raises `StoreIntegrityError`, including
invalid snapshot schema/definition/policy/admitted fields or a terminal consume
receipt missing its committed watermark. A matching index conflict cannot
hide an unrelated constraint failure. The insertion uses
`ON CONFLICT(occurrence_id,attempt) DO NOTHING RETURNING run_id`; only a newly
inserted row authorizes projection. Busy errors remain SQLite busy for bounded
caller retry. Stale state uses `StoreConflict`/`JobNotFound`; invalid supplied
authority/input fails without writes. No caller transaction is permitted.

## Explicitly partial overlap scope

The accepted store has no common terminal projection or executor/retry
supersession interface. Implementing only a skipped receipt here would omit
the shared §3.4.4 consumption effects. This slice therefore uses the task's
explicit no-write deferral option for recurring overlap. It creates no queued
intermediate or terminal overlap row, consumes no slot, and leaves the active
receipt and its owner/snapshots unchanged. Merely queued retries take a
distinct deferred result. Direct-terminal overlap plus common atomic
projection is still required before recurring busy scheduling is complete.

An authored at that crosses due while a borrower is active similarly retains
its original slot, next time, W and counters. After a fixture clears that
active row, the same slot can be reserved once. These tests deliberately seed
terminal borrower outcomes; they do not implement or claim borrower
finalization, restart repair or later authored terminal consumption.
